### Schwab multi-account scope fix (2026-08-03)
Driven by `prompts/schwab_account_scope_fix_2026-08-03.md`, following the discovery (same day, via `AI_Suggested_Allocation`-triggered analysis) that the 2026-08-02 composite bundle reported `total_value: $897,748.49` against the Sheet's known-correct ~$591-596K KPI, with JEPI/JPIE weights ~3.5x too high while `Trade_Log` showed net *selling* in both over the same window.
- **Root cause, confirmed by code inspection then by a live read-only `get_accounts()` call**: `fetch_positions()`/`fetch_transactions()`/`fetch_tax_lots()` in `utils/schwab_client.py` aggregated every account the API token could see, with zero account-level filtering anywhere in the codebase. **The live enumeration found SIX linked accounts, not the three the repo's CSV exports implied** — with heavily overlapping holdings (JEPI in 5 of 6, QQQM/VTI/GOOG/AMZN/NVDA/COF/EWZ/XBI/VEA/IBM/XOM/UNH/EMXC/ES/GILD/IFRA/WSM/APO/MELI each in multiple). None of the six accounts' Schwab `type` field contains `IRA`/`ROTH`/`401`/`QRP` — they're all just `CASH` or `MARGIN` (a settlement-type distinction, not a tax-treatment one) — so the account `type` field the code was reading for tax-treatment classification was never going to carry a 401(k)/IRA signal for this Schwab connection in the first place, independent of the ROTH/IRA-substring bug that was also fixed.
- **Primary scope, confirmed by Bill against live masked-account evidence**: the ~$591-596K portfolio this system represents is the **sum of three of the six accounts** — masked `...6499`, `...8767`, `...5119` ($595,405.90 combined at enumeration time). The other three (`...4151`, `...0217`, `...9753`, ~$309K combined) are out of scope. `config.SCHWAB_PRIMARY_ACCOUNT_SUFFIXES` (default `["6499","8767","5119"]`, overridable via env var) now gates all three fetch functions in `utils/schwab_client.py`; empty list = old unscoped behavior, with a one-time warning logged if left empty.
- **A first guess was wrong and is worth remembering as a cautionary example**: before the live enumeration, `Individual_XXX119` (the repo's CSV filename) looked like a reasonable single-account identifier. Testing that guess live (`SCHWAB_PRIMARY_ACCOUNT_SUFFIX=119`, since retired) produced `$388,785.88`/34 positions — missing XLF/ET/KRE/NOW entirely (they live in the other in-scope accounts) — a *different* wrong number, not a fix. It matched account `...5119` alone, which is real but only one of the three that make up the actual scope. Verified live before shipping, not assumed from a filename.
- **Tax-treatment classifier extended** (`_classify_tax_treatment()`, new shared helper used by `fetch_positions()` and `fetch_tax_lots()`, replacing two independent copies of the same ROTH/IRA-only check) to also recognize `401`/`QRP` account types, mapped to `tax_deferred` (same bucket as IRA, per Bill's confirmation — no downstream consumer currently needs a finer distinction). ### High-signal moment extraction (`tasks/extract_moments.py`, shipped 2026-08-02)
- Second, distinct extraction pass over podcast transcripts, parallel to `podcast_analyst.PodcastStrategy` (macro-allocation summarization). This one pulls out specific, falsifiable, verbatim moments — a conviction reversal, a non-consensus claim, a disclosed position, a specific numeric claim, or a disagreement between speakers — scored only against "does this change what Bill holds, or what he'd consider holding." Driven by `prompts/moment_extraction_2026-08-02.md`; the prompt file itself was revised twice mid-build (see below) and is worth reading for the design reasoning, not just the final shape.
- **Two-stage architecture, not one.** `utils/moment_windows.py` (`find_windows()`) is pure Python cue-phrase windowing — no LLM, no network, deterministic, unit-tested (`tests/test_moment_windows.py`). `utils/agents/moment_extractor.py` calls Gemini per window and is **position-independent by design**: it extracts and verbatim-validates a fragment and caches it to `data/moments/{transcript_stem}.moments.json`, but never resolves or persists a `relevance` tag. Relevance (`HELD`/`THESIS_ON_FILE`/`ADJACENT`/`ZERO_EXPOSURE`) is a cheap, position-dependent Python lookup computed fresh every time the cache is read — the position set is mutable, the transcript and its moments are not, and caching a mutable answer would silently rot (verified: aggregate `['VST','NRG']` moment stays `HELD` either way since VST is held, but `NRG` alone resolves `ZERO_EXPOSURE` before a hypothetical open and `HELD` after — the recompute-on-read mechanism confirmed against real cached data, not synthetic).
- **`export_ai_briefing.py` remains genuinely network-free.** `build_moments_md()` only reads `data/moments/*.json` — no `--moments` flag exists or was added; the docstring's "no network calls" invariant was treated as structural, not something to weaken with an opt-in. Extraction is a separate, cached, idempotent step (`python manager.py extract-moments [--force NAME] [--limit N]`), wired as STEP 4c of `pm morning` (after podcast sync, before the composite bundle/export steps), non-fatal on a single transcript's failure.
- **ADJACENT relevance deliberately excludes GICS sector**, and not for a data-availability reason — sector is empty on every position in the bundle and cached for only 2 of 38 tickers elsewhere, but the real problem is that 38 positions span nearly every sector, so a working sector match would empty the `ZERO_EXPOSURE` bucket this build exists to populate. Rejected outright, documented in `utils/agents/moment_extractor.py`'s module docstring as **do not re-add even once the FMP-sector-bundle gap closes**. ADJACENT resolves via ETF look-through (cached, no new network) plus a new leg: ticker/company name mentioned in the body of some *other* thesis file (e.g. real example found in verification: `TSM` → `ADJACENT` via `TSMC` mentioned in `EMXC_thesis.md`'s body).
- **Two distinct static rank orders in `podcasts.md`'s new `## High-Signal Moments` block** — `position_disclosure` sorts first in `### Zero-Exposure Ideas` (a manager's own-money conviction stake in a name Bill doesn't hold is the highest-value idea signal) and last in the main section (the same disclosure about a name already held is confirmation fodder). Capped at 8/day total, round-robin allocated between the two subsections so a naive cap can't silently bury zero-exposure ideas. Zero-exposure share of total moments and the Python-vs-Gemini relevance disagreement rate are both printed in the block itself, not just logged — verification run showed 3/7 disagreements and a 43% zero-exposure share on a small real sample.
- **Two bugs found and fixed during verification, not in the original build**: `max_tokens=1000` on the per-window Gemini call was too small for gemini-2.5-pro's schema overhead and silently truncated several real responses mid-JSON (raised to 2000); `extract_moments.py`'s `--limit` counted only successes toward its cap, so a string of real failures would blow through the throttle and attempt the entire remaining corpus instead of stopping at N (fixed to count total attempts).
- **Backfill is partial, not deferred by choice.** An operator error mid-verification (a re-run intended to test idempotency on 5 files instead kicked off the default full-corpus scan) left 66/147 transcripts genuinely cached before being stopped — 19 real moments extracted, no corrupted cache files, confirmed idempotent (re-running with the remaining 81 uncached performs zero Gemini calls against the 66 already done). The remaining ~81 are intentionally left for a deliberate, throttled run: `python manager.py extract-moments --limit N`.

#### v2 fix (2026-08-02, same day) — fragment context, portfolio-hook filter, cue recall
Driven by `prompts/moment_extraction_v2_fix_2026-08-02.md`. v1's 66-transcript sample yielded 19 moments (79% of transcripts zero) with a fragment length so short (<=15 words verbatim) it was routinely unusable — `"And we bought it in January"` (bought *what*?), `"I own two software stocks"` (which ones?). A Step 0 diagnostic (free, no Gemini) attributed the low yield almost entirely to windowing recall, not judge over-rejection: 0.41 windows/transcript, 50/66 zero, ~70% Gemini acceptance of what it *was* given.
- **`context: str` field added to `MomentCandidate`** — 400-800 chars Python-sliced from the source transcript, centered on the fragment's actual position, sentence/turn-boundary-snapped where cheap. Gemini's response schema (`GeminiMomentResponse`) has no `context` field at all, so it structurally cannot generate one — the field is a slicing operation on already-verified transcript text, not a model output. `fragment in context` is validated as a stronger version of the old `fragment in window text` check.
- **Cache schema bumped to `{"schema_version": 2, "moments": [...]}`** (was a bare list). `extract_moments.py` treats a missing/old version as stale and re-extracts; all 66 v1 files were correctly detected as stale (verified) and are excluded from `build_moments_md()`'s render until re-extracted, rather than crashing on the missing `context` field.
- **Ticker-proximity gate was a structural bug, not a tuning knob.** v1's `ticker_aliases.json` covered only the 37 held tickers, so `specific_claim` could only ever fire next to a name Bill already owned — **zero-exposure discovery was impossible by construction**, the exact opposite of the build's purpose. Fixed three ways: (1) `scripts/generate_ticker_aliases.py` regenerates the alias file from the public S&P 500 constituents dataset (547 tickers, up from 37; a small hand-curated ADR supplement added on top; FMP's own `/stable/sp500-constituent` is gated above the current subscription tier, confirmed via a live 402) — preserves and only adds to existing hand-curated entries, never overwrites them; (2) `specific_claim` proximity relaxed from 120 chars to 1200 (the full window) since spoken podcasts never use ticker symbols, only company names, so a tight radius was actively working against recall; (3) a capitalized-multi-word-proper-noun fallback heuristic proposed in the fix prompt was **not implemented** — this transcript corpus is 100% lowercase auto-captions with no capitalization signal at all (confirmed in the v1 build's own Step 0), so that heuristic cannot fire on real data here; the broadened alias list + relaxed proximity address the same recall gap without requiring a signal the corpus doesn't have.
- **Five written-English cue patterns had zero hits across the full 147-transcript corpus** (`"we exited"`, `"I've changed my mind"`, `"I was wrong about"`, `"nobody is talking about"`, `"the thing people miss"`) — kept (cost nothing), supplemented with spoken variants in `data/moment_cues.json` (`"we got out of"`, `"turns out I was wrong"`, `"what people are missing"`, etc.).
- **New no-portfolio-hook filter** (`passes_portfolio_hook_filter()`, read-time only) drops a candidate entirely — not even `ZERO_EXPOSURE` — when it has no ticker, no held-name mention in its context, and isn't a reversal with a macro term (`data/moment_cues.json`'s new `macro_terms` list) nearby. Kills the "musing about AI" and "unrelated private-market anecdote" false positives v1 shipped.
- **Real bug caught by this fix's own live verification, not by unit tests**: the no-hook filter's alias check force-included the bare ticker symbol for every held ticker, silently reintroducing exactly the SNOW/GILD/ES/ET/NOW/META collision class `ticker_aliases.json` was built to avoid — the Myrtle Beach hotel record (the checklist's own named regression test) initially *survived* the filter because "at least **now** we are one of the largest owners..." false-matched ticker `NOW`. Fixed in both `passes_portfolio_hook_filter()` and the pre-existing (same bug, present since v1) `_mentioned_in_other_thesis()` ADJACENT-leg helper — both now trust `ticker_aliases.json` as the sole source of truth for what's safe to bare-match, never forcing the ticker symbol in on top.
- **Live 10-transcript re-extraction sample** (hand-picked from the 66 already-cached, via a new `only=[...]` param on `run_extract_moments()` that bypasses the corpus scan entirely — the safe way to re-extract a named sample without risking another full-corpus run): 31 windows, 25 candidates, yield 2.5 moments/transcript (up from v1's 0.29 baseline), zero-exposure discovery proven with multiple real non-held names in a single run (WMT, FND, IBIT/MSTR, FIS/MFC/PAYX — structurally impossible under v1). `dropped_by_reason` now instrumented and persisted per run to `logs/moment_extraction_runs.jsonl`.
- **`speaker` correction, not a bug**: audited the claim that "every record carries `speaker: unknown`" — false as a generalization. It correctly populates a real `>>` turn index (e.g. `turn_81`) for the one `disagreement`-type cue, which is the only category that was ever designed to carry positional speaker info; the other four categories correctly show `unknown` since no `>>`-proximity signal was ever computed for them. No code change was the right call here.

### Basket-aware rotation attribution (`tasks/compute_rotation_attribution.py`, 2026-08-08)
Driven by `prompts/build_basket_attribution_2026-08-08.md`. The basket (multi-ticker sell → multi-ticker buy) is the unit of analysis — not synthetic pairs.
- Dollar weights reconstructed from `Transactions` and reconciled to stated `Sell_Proceeds`/`Buy_Amount` within 2% (else `WEIGHTS_UNRECONCILED`, no silent fallback to equal weight).
