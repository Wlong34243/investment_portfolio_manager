### Schwab multi-account scope fix (2026-08-03)
Driven by `prompts/schwab_account_scope_fix_2026-08-03.md`, following the discovery (same day, via `AI_Suggested_Allocation`-triggered analysis) that the 2026-08-02 composite bundle reported `total_value: $897,748.49` against the Sheet's known-correct ~$591-596K KPI, with JEPI/JPIE weights ~3.5x too high while `Trade_Log` showed net *selling* in both over the same window.
- **Root cause, confirmed by code inspection then by a live read-only `get_accounts()` call**: `fetch_positions()`/`fetch_transactions()`/`fetch_tax_lots()` in `utils/schwab_client.py` aggregated every account the API token could see, with zero account-level filtering anywhere in the codebase. **The live enumeration found SIX linked accounts, not the three the repo's CSV exports implied** — with heavily overlapping holdings (JEPI in 5 of 6, QQQM/VTI/GOOG/AMZN/NVDA/COF/EWZ/XBI/VEA/IBM/XOM/UNH/EMXC/ES/GILD/IFRA/WSM/APO/MELI each in multiple). None of the six accounts' Schwab `type` field contains `IRA`/`ROTH`/`401`/`QRP` — they're all just `CASH` or `MARGIN` (a settlement-type distinction, not a tax-treatment one) — so the account `type` field the code was reading for tax-treatment classification was never going to carry a 401(k)/IRA signal for this Schwab connection in the first place, independent of the ROTH/IRA-substring bug that was also fixed.
- **Primary scope, confirmed by Bill against live masked-account evidence**: the ~$591-596K portfolio this system represents is the **sum of three of the six accounts** — masked `...6499`, `...8767`, `...5119` ($595,405.90 combined at enumeration time). The other three (`...4151`, `...0217`, `...9753`, ~$309K combined) are out of scope. `config.SCHWAB_PRIMARY_ACCOUNT_SUFFIXES` (default `["6499","8767","5119"]`, overridable via env var) now gates all three fetch functions in `utils/schwab_client.py`; empty list = old unscoped behavior, with a one-time warning logged if left empty.
- **A first guess was wrong and is worth remembering as a cautionary example**: before the live enumeration, `Individual_XXX119` (the repo's CSV filename) looked like a reasonable single-account identifier. Testing that guess live (`SCHWAB_PRIMARY_ACCOUNT_SUFFIX=119`, since retired) produced `$388,785.88`/34 positions — missing XLF/ET/KRE/NOW entirely (they live in the other in-scope accounts) — a *different* wrong number, not a fix. It matched account `...5119` alone, which is real but only one of the three that make up the actual scope. Verified live before shipping, not assumed from a filename.
- **Tax-treatment classifier extended** (`_classify_tax_treatment()`, new shared helper used by `fetch_positions()` and `fetch_tax_lots()`, replacing two independent copies of the same ROTH/IRA-only check) to also recognize `401`/`QRP` account types, mapped to `tax_deferred` (same bucket as IRA, per Bill's confirmation — no downstream consumer currently needs a finer distinction). This is a real, correct fix to a real gap, but per the finding above it has nothing to match against in the six real accounts currently linked; it protects against a genuine 401(k)-type account being linked in the future.
- **Style-ceiling override bug fixed** (`core/thesis_sync_data.py`, `tasks/export_ai_briefing.py`) — a thesis file's own `style_size_ceiling_pct` frontmatter override (nested under `triggers:`, e.g. META's `4.0` vs the GARP style default of `9.0`) was being silently ignored on both the read side (`build_ceiling_check()` always used the style default) and, more seriously, the write side (`thesis_sync_data.py` always recomputed the style default, so `write_thesis_updates.py` would overwrite a manual override back to the default on every sync — destructive, not cosmetic). Both sides now check the thesis file's own override first. Verified directly against the real `META_thesis.md`: override resolves to `4.0` on both the sync path and a live `build_ceiling_check()` render (synthetic 5.79% weight → 1.79% drift against the 4.0 ceiling, not 6.79% against 9.0).
- **Live-verified end-to-end, not just unit-tested**: a real (dry-run, no Sheet writes) `manager.py snapshot --source auto` with the fix active returned `total_value: $595,527.33`, 38 positions — inside the known-correct range. JEPI/JPIE now show 815/335 shares (down from the pre-contamination 881/460, consistent with real net selling in `Trade_Log` over the window) rather than the contaminated 5131/1460.
- **Known residual gap, out of scope for this fix**: whether any `sync_transactions.py --live` run happened 2026-08-02 or later (after the scope apparently expanded) and pulled 401(k)/Contributory-adjacent transactions into `Transactions`/`Trade_Log` needs a manual check of Sheet version history — not attempted here per the prompt's explicit instruction not to touch those tabs.

### High-signal moment extraction (`tasks/extract_moments.py`, shipped 2026-08-02)
- Second, distinct extraction pass over podcast transcripts, parallel to `podcast_analyst.PodcastStrategy` (macro-allocation summarization). This one pulls out specific, falsifiable, verbatim moments — a conviction reversal, a non-consensus claim, a disclosed position, a specific numeric claim, or a disagreement between speakers — scored only against "does this change what Bill holds, or what he'd consider holding." Driven by `prompts/moment_extraction_2026-08-02.md`; the prompt file itself was revised twice mid-build (see below) and is worth reading for the design reasoning, not just the final shape.
- **Two-stage architecture, not one.** `utils/moment_windows.py` (`find_windows()`) is pure Python cue-phrase windowing — no LLM, no network, deterministic, unit-tested (`tests/test_moment_windows.py`). `utils/agents/moment_extractor.py` calls Gemini per window and is **position-independent by design**: it extracts and verbatim-validates a fragment and caches it to `data/moments/{transcript_stem}.moments.json`, but never resolves or persists a `relevance` tag. Relevance (`HELD`/`THESIS_ON_FILE`/`ADJACENT`/`ZERO_EXPOSURE`) is a cheap, position-dependent Python lookup computed fresh every time the cache is read — the position set is mutable, the transcript and its moments are not, and caching a mutable answer would silently rot (verified: aggregate `['VST','NRG']` moment stays `HELD` either way since VST is held, but `NRG` alone resolves `ZERO_EXPOSURE` before a hypothetical open and `HELD` after — the recompute-on-read mechanism confirmed against real cached data, not synthetic).
- **`export_ai_briefing.py` remains genuinely network-free.** `build_moments_md()` only reads `data/moments/*.json` — no `--moments` flag exists or was added; the docstring's "no network calls" invariant was treated as structural, not something to weaken with an opt-in. Extraction is a separate, cached, idempotent step (`python manager.py extract-moments [--force NAME] [--limit N]`), wired as STEP 4c of `pm morning` (after podcast sync, before the composite bundle/export steps), non-fatal on a single transcript's failure.
- **ADJACENT relevance deliberately excludes GICS sector**, and not for a data-availability reason — sector is empty on every position in the bundle and cached for only 2 of 38 tickers elsewhere, but the real problem is that 38 positions span nearly every sector, so a working sector match would empty the `ZERO_EXPOSURE` bucket this build exists to populate. Rejected outright, documented in `utils/agents/moment_extractor.py`'s module docstring as **do not re-add even once the FMP-sector-bundle gap closes**. ADJACENT resolves via ETF look-through (cached, no new network) plus a new leg: ticker/company name mentioned in the body of some *other* thesis file (e.g. real example found in verification: `TSM` → `ADJACENT` via `TSMC` mentioned in `EMXC_thesis.md`'s body).
